## 三、逐项分析

### 3.1 变更1：teaching_class 新增 grade 字段

#### 3.1.1 数据库层

**现状**：

```sql
-- teaching_class 当前结构
CREATE TABLE `teaching_class` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `course_id` bigint NULL COMMENT '课程',
  `teacher_id` bigint NULL COMMENT '主讲教师',
  `semester_id` bigint NULL COMMENT '开课学期',
  `class_name` varchar(50) NULL COMMENT '班级名称',
  PRIMARY KEY (`id`)
);
```

**变更**：

```sql
ALTER TABLE `teaching_class`
  ADD COLUMN `grade` int(0) NULL COMMENT '年级（入学年份），如 2024 表示 2024 级',
  ADD INDEX `idx_grade` (`grade`);
```

**影响评估**：

| 维度 | 评估 |
|------|------|
| SQL 兼容性 | ✅ `INT NULL` 完全兼容，新字段允许 NULL 保证向后兼容 |
| 索引开销 | ✅ 单列 INT 索引极小，对性能无影响 |
| 现有数据 | ⚠️ 需回填（见 3.1.2） |
| 外键 | ❌ 不需要外键 — grade 是业务标签，不引用字典表 |

#### 3.1.2 现有数据回填

当前8个教学班与年级的对应关系（可从 `class_name` 或 `class_student → student.enrollment_year` 推断）：

### 3.2 变更2：第三级计算增加年级下拉选项

#### 3.2.1 后端变更点

需要修改的方法链：`GlobalCalcController → GlobalCalcService.getDashboard()`

**（A）`getDashboard()` 增加年级过滤**

```java
// 当前（第49行）：只按 majorId 过滤
public DashboardData getDashboard(Long majorId)

// 修改后：增加 grade 参数
public DashboardData getDashboard(Long majorId, Long semesterId, Integer grade)
```

内部加载教学班时增加年级条件（第68-69行处）：

```java
// 当前：
List<TeachingClass> classes = teachingClassMapper.selectList(
    new LambdaQueryWrapper<TeachingClass>()
        .eq(TeachingClass::getCourseId, course.getId()));

// 修改后：
LambdaQueryWrapper<TeachingClass> wrapper = new LambdaQueryWrapper<TeachingClass>()
    .eq(TeachingClass::getCourseId, course.getId());
if (grade != null) {
    wrapper.eq(TeachingClass::getGrade, grade);  // ← 新增
}
List<TeachingClass> classes = teachingClassMapper.selectList(wrapper);
```

**（B）`compute()` 传递年级参数**

```java

// 修改后：增加 grade 参数
public MajorCalcResult compute(Long majorId, Long semesterId, Integer grade, Long operator)
```

第一行调用改为：
```java

```

**（C）Controller 接收年级参数**

```java
// 当前：

// 修改后：grade 为可选参数

public Result<...> compute(@RequestParam Long majorId,
                           @RequestParam Long semesterId,
                           @RequestParam(required = false) Integer grade,
                           @RequestParam Long operator)
```

**（D）年级选项数据源**

前端下拉选项的值来源于 `student.enrollment_year` 的 DISTINCT 值，或新建一个年级字典。建议直接查询：

```sql
SELECT DISTINCT enrollment_year FROM student
WHERE major_id = ? AND enrollment_year IS NOT NULL
ORDER BY enrollment_year DESC;
```

当前数据可选项：`2024`, `2025`。

#### 3.2.2 计算影响链分析

选择年级后，完整的影响链如下：

```
用户选择 grade=2025
    ↓
getDashboard(majorId=1, semesterId=1, grade=2025)
    ↓ 只加载 grade=2025 的教学班
    ↓ 返回: class 1, 2, 3, 4（共4个班）
    ↓
权重归一化基于这4个班的 macro_support_matrix 权重
    ↓ （课程8无班→自动排除，课程4/7无grade=2025的班→也排除）
    ↓ 指标点1 有效权重: 仅课程1(10%) → sum=0.1 → 归一化×10 → 100%
    ↓
专业第三级 major_achievement: 基于 class 1-4 的结果 ✅
学生个人第三级 personal_achievement: 仅处理 class 1-4 中的学生 ✅
```

#### 3.2.3 与 semester 方案的对比

| 维度 | semester 过滤（备选） | grade 过滤（用户方案） |
|------|----------------------|----------------------|
| 实现难度 | 极低（改1行代码） | 低（新增字段+改几行） |
| 是否需要改表 | ❌ 不需要 | ✅ 需要 ALTER TABLE |
| 分离2024/2025级 | ✅ 当前数据有效 | ✅ 始终有效 |
| 同一年级跨学期聚合 | ❌ 需多次计算后合并 | ✅ 一次计算即可 |
| 未来多年级同学期场景 | ❌ 无法分离 | ✅ 天然支持 |
| 语义清晰度 | 一般（"学期"≠"年级"） | ✅ 高（"年级"=业务概念） |

**关键场景**：假设 2025-2026 学年同时有 2024 级（大二）和 2025 级（大一）的课程：

- **semester 方案**：semester=1 时两个年级的课程混在一起，无法分离
- **grade 方案**：grade=2024 只选大二课程，grade=2025 只选大一课程 ✅

## 四、边缘情况与风险分析

### 4.1 边缘情况1：一个教学班包含多年级学生（如重修生）

**场景**：`计算机网络202501` 班级（grade=2025）中有 2024 级重修学生。

**影响**：
- 班级级别：`grade` 是教学班的属性，"2025 级计算机网络班"仍归属于 2025 级 → 与年级下拉选项一致 ✅
- 学生级别：重修生的个人第三级会被计入 2025 级的计算批次中 → 该生在 2024 级中也应有独立记录

**处理建议**：
- 班级的 `grade` 字段设为该班的"目标年级"（即大多数学生的年级）
- 重修学生的跨年级问题通过 `personal_achievement` 表独立存储来解决（该生在不同年级的 MAJOR 级记录通过 `majorId+semesterId` 组合键区分）
- **当前数据中不存在此情况**，短期可暂不处理

### 4.2 边缘情况2：grade=NULL 的旧数据

**场景**：未来导入的教学班未指定年级。

**影响**：`grade IS NULL` 的班级在 `wrapper.eq(..., grade)` 时会被排除。

**处理建议**：
- 新建教学班时强制填写年级（前端表单加必填校验）
- 存量数据回填脚本覆盖所有现有班级
- `getDashboard()` 中 `grade=null` 时不过滤（即 `if (grade != null)` 条件），保留兼容性

### 4.3 边缘情况3：专业级和年级级的关系

**场景**：`major_achievement` 表存储专业级第三级结果。引入年级后，是否需要同时存储年级维度的专业级结果？

**回答**：不需要。`major_achievement` 的 `semester_id` 字段已能区分不同计算批次。引入年级后，`compute(majorId, semesterId, grade=2025)` 和 `compute(majorId, semesterId, grade=2024)` 是两次独立计算，各有独立结果，同一条 `semester_id` 下可存多条记录。

但建议将 `major_achievement` 的唯一约束扩展为包含年级：

```sql
-- 当前：
UNIQUE INDEX `uk_major_indicator_semester`(`major_id`, `indicator_id`, `semester_id`)

-- 建议：
UNIQUE INDEX `uk_major_indicator_semester_grade`
    (`major_id`, `indicator_id`, `semester_id`, `grade`)
```

或者更简单地，不同年级用不同的 `semester_id` 区分计算批次。

### 4.4 风险总结

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 年级字段未填写导致班级被排除 | 🟡 低 | 前端必填校验 + 后端非NULL约束（可逐步推进） |
| 重修生跨年级归属 | 🟢 极低 | 当前数据不存在此情况，后续可通过个人达成度表独立处理 |
| 年级与 semester 不一致 | 🟡 低 | 新建教学班时做一致性校验（如 grade=2024 的班不应开在 2026-2027 学期） |
| 前端下拉选项过期 | 🟢 极低 | 从 `student.enrollment_year` 动态获取 |

## 五、建议补充：同时修复 semester 过滤

虽然 `grade` 方案解决年级分离问题，但 `semester_id` 参数被忽略的 Bug 仍然存在。建议**同时修复**：

```java
public DashboardData getDashboard(Long majorId, Long semesterId, Integer grade) {
    ...
    LambdaQueryWrapper<TeachingClass> wrapper = new LambdaQueryWrapper<TeachingClass>()
        .eq(TeachingClass::getCourseId, course.getId());
    if (semesterId != null) {
        wrapper.eq(TeachingClass::getSemesterId, semesterId);  // ← 修复原 Bug
    }
    if (grade != null) {
        wrapper.eq(TeachingClass::getGrade, grade);            // ← 新增年级过滤
    }
    ...
}
```

这样用户可以选择：
- **仅按年级**：`?grade=2025` → 该年级所有学期的班级
- **仅按学期**：`?semesterId=1` → 该学期所有年级的班级
- **年级+学期**：`?grade=2025&semesterId=1` → 精确到某年级某学期
- **全部**：都不传 → 全专业所有班级（兼容旧行为，用于专业级全量计算）
