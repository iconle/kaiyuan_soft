# 三级计算正确性与学生个人达成度分析报告

**报告日期**：2026-06-28  
**分析对象**：面向专业认证的毕业要求达成度统一计算平台  
**数据来源**：`sql/obe_platform.sql`、`docs/material/软件需求规格说明书.md`、后端源码（Java/Spring Boot）

---

## 一、系统架构总览

系统采用"宏观矩阵-微观大纲"双层权重设计，自下而上三级计算：

```
原始成绩 (student_score)
    ↓ 按考核点→目标映射
[第一级] 课程目标级达成度 (obj_achievement)     ← 教师触发
    ↓ 乘内部贡献权重 w_jk
[第二级] 课程级指标点达成度 (course_achievement)  ← 教师触发
    ↓ 乘宏观支撑权重 W_c
[第三级] 专业级指标点达成度 (major_achievement)   ← 专业负责人/教务触发
```

对应的学生个人达成度存储在 `personal_achievement` 表中，按 `scope_type` 区分三级。

## 二、第一级：课程目标级达成度分析

### 2.1 需求规格公式

$$C_{ij} = \frac{\sum (\text{支撑目标 } j \text{ 的考核点实际得分})}{\sum (\text{支撑目标 } j \text{ 的考核点目标满分})}$$

班级目标达成度 $\bar{C_j}$ = 全体学生 $C_{ij}$ 的算术平均值。

### 2.2 代码实现

**文件**：`backend/.../engine/Level1Calculator.java`

核心逻辑：
1. 筛选与目标 `objectiveId` 关联的考核点（含题目级）
2. 按学生分组，分别计算 `actualSum / maxSum`
3. 汇总所有学生达成度，求算术平均

支持两层粒度：
- **考核点级**：通过 `assessment_objective` 表（N:M）或 `assessment_point.objective_id` 获取映射
- **题目级**：通过 `question_objective` 表获取更细粒度的映射；若某考核点有题目级数据，优先使用题目级

### 2.3 正确性判断：✅ 正确

| 检查项 | 结论 |
|--------|------|
| 公式实现与规格一致 | ✅ 分子=Σ实际得分，分母=Σ满分，学生平均 |
| N:M 考核点-目标多对多映射 | ✅ 同一考核点得分计入所有关联目标 |
| 题目级粒度优先于考核点级 | ✅ 有题目数据时使用题目级，避免重复计算 |
| 精度处理 | ✅ BigDecimal + HALF_UP 舍入，6位中间精度→4位最终精度 |
| 零分母保护 | ✅ maxSum=0 时该学生不计入 |

### 2.4 注意事项

- **考核点 `weight_percent` 字段未参与计算**：该字段（如 20%、25%）为信息性字段，表示该考核点占总成绩的百分比，但 Level1 公式严格按实际得分/满分计算，不使用权重。这与规格一致。
- **同一考核点支撑多目标的"双重计数"**：例如考核点1绑定目标1和目标2，学生得分 85/100，则两个目标均计入 85/100。这是规格明确的设计意图。

## 三、第二级：课程级达成度分析

### 3.1 需求规格公式

$$E_{k} = \sum_{j} \left( \bar{C_j} \times w_{jk} \right)$$

约束：针对同一指标点 $k$，$\sum w_{jk} = 1.0$

### 3.2 代码实现

**文件**：`backend/.../engine/Level2Calculator.java`

核心逻辑：
1. 验证每个指标点的权重之和 ≈ 1.0（容差 ±0.01）
2. 对每个权重记录计算 contribution = C̄_j × w_jk
3. 按指标点汇总所有 contribution

### 3.3 正确性判断：✅ 正确

| 检查项 | 结论 |
|--------|------|
| 加权求和公式与规格一致 | ✅ E_k = Σ(C̄_j × w_jk) |
| 权重归一化校验 | ✅ 容差 0.01，不一致时抛出异常 |
| 精度处理 | ✅ BigDecimal HALF_UP，4位小数 |

### 3.4 注意事项

- **权重校验存在两处重复**：`Level2Calculator.calcCourseAchievement()`（第29-33行）和 `CourseCalcService.compute()`（第163-173行）各执行一次校验。功能上无问题，但为代码冗余，建议统一在计算引擎层校验。
- **当某目标的 C̄_j 不存在时默认为 0**：代码第41行 `achievement = BigDecimal.ZERO`。这意味着如果某个课程目标没有考核点数据，其达成度默认视为 0。

## 第四级：第三级（专业级）达成度分析

### 4.1 需求规格公式

$$G_{k} = \sum \left( E_{k} \times W_{c} \right)$$

约束：全专业内，支撑同一指标点 $k$ 的相关课程，$\sum W_{c} = 1.0$

### 4.2 代码实现

**文件**：`backend/.../engine/Level3Calculator.java` + `GlobalCalcService.java`

核心逻辑（`GlobalCalcService.compute()`）：
1. 检查所有相关课程是否已完成 Level2 计算（状态=LOCKED）
2. 获取宏观支撑矩阵权重
3. **关键步骤：多班级权重拆分** — 若一门课程有多个教学班，宏观权重 $W_c$ 等分给各班
4. **归一化**：若各班权重之和 ≠ 1.0，按比例归一化
5. 调用 Level3Calculator 执行加权求和

### 4.3 正确性判断：✅ 正确（含适应性设计）

| 检查项 | 结论 |
|--------|------|
| 加权求和公式与规格一致 | ✅ G_k = Σ(E_k × W_c) |
| 前置校验（全部锁定） | ✅ 任一课程未锁定则拒绝计算 |
| 精度处理 | ✅ BigDecimal HALF_UP，4位小数 |

### 4.4 与规格的偏差分析

#### 偏差1：多班级权重均分

规格中 $W_c$ 是课程级别的权重（一门课一个值），但实际系统中一门课可能有多个教学班级。代码将 $W_c$ 等分给每个班级。

**评价**：这是对现实场景的合理适配。规格的简化模型假设一课一班，但实际存在一课多班。等分策略默认各班同等重要，符合一般认知。

#### 偏差2：权重自动归一化

规格要求 $\sum W_c = 1.0$ 且不满足时禁止提交（A-4）。代码在 `GlobalCalcService` 中对分班后的权重执行自动归一化，而非拒绝。

**评价**：
- 前端界面已有校验（规格 A-4），正常情况下权重应已满足归一化
- 自动归一化主要用于处理分班后精度舍入导致的微小偏差（如 0.3333+0.3333+0.3333=0.9999）
- **风险**：如果原始宏观权重配置错误（如总和=0.5），将被悄无声息地"修正"为 1.0，实际权重翻倍，可能掩盖配置错误

#### 偏差3：仅统计有教学班的课程

`GlobalCalcService.compute()` 第137-141行只对"有教学班"的课程进行权重校验和计算。无教学班的课程即使在宏观矩阵中配置了权重，也不参与计算。

**评价**：合理设计 — 无教学班即无实际数据，不应参与达成度计算。但这些课程的权重被静默排除，可能导致有效权重之和 < 1.0，被归一化步骤修正。

### 4.5 宏观权重数据抽查验证

以指标点 3 为例，`macro_support_matrix` 表中相关记录：

| 课程 | weight | 教学班数 |
|------|--------|----------|
| 数据结构(1) | 0.3000 | 1 |
| C语言(5) | 0.3000 | 1 |
| 大学物理(6) | 0.4000 | 1 |
| **总和** | **1.0000** | |

该指标点权重之和恰好为 1.0，计算正确。

## 五、学生个人达成度分析

### 5.1 核心问题：后端计算还是数据库存储？

**答案：两者皆有 — 后端实时计算 + 数据库持久化存储，读取时 DB 优先。**

### 5.2 详细流程

#### 存储机制

学生个人达成度通过 `personal_achievement` 表持久化，以 `scope_type` 字段区分三级：

| scope_type | 含义 | 对应字段 |
|------------|------|----------|
| `OBJECTIVE` | 学生个人第一级（目标级） | `objective_id` |
| `COURSE` | 学生个人第二级（课程级） | `indicator_id` |
| `MAJOR` | 学生个人第三级（专业级） | `indicator_id` + `major_id` + `semester_id` |

#### 写入时机

| 级别 | 触发操作 | 代码位置 |
|------|----------|----------|
| OBJECTIVE & COURSE | 教师点击"课程级达成度计算"（Phase 1） | `CourseCalcService.compute()` → `PersonalAchievementService.persistClassAchievements()` |
| MAJOR | 专业负责人点击"专业级全局计算"（Phase 2） | `GlobalCalcService.compute()` → `PersonalAchievementService.persistMajorAchievements()` |

#### 读取策略

`PersonalAchievementService` 采用 **DB 优先、实时回退** 策略：

```java
// getClassDetails() 方法 (第250-256行)
private List<StudentAchievementDetail> getClassDetails(Long classId) {
    List<StudentAchievementDetail> persisted = listPersistedClassDetails(classId);
    if (!persisted.isEmpty()) {
        return persisted;  // DB 有数据 → 直接返回
    }
    return calculateClassDetails(classId);  // DB 无数据 → 实时计算
}
```

### 5.3 学生个人第一级（目标级）计算

**代码**：`PersonalAchievementService.calculateStudent()` → `Level1Calculator.calcObjectiveAchievement()`

计算公式（与班级级共用同一引擎）：

$$C_{ij}^{student} = \frac{\sum (\text{该生支撑目标}j\text{的考核点得分})}{\sum (\text{支撑目标}j\text{的考核点满分})}$$

**正确性**：✅ 正确。与班级第一级使用相同的 `Level1Calculator`，区别在于：
- 班级级：计算所有学生的 $C_{ij}$ 后求平均 → $\bar{C_j}$
- 学生级：仅计算单个学生的 $C_{ij}$

### 5.4 学生个人第二级（课程级）计算

**代码**：`PersonalAchievementService.calculateStudent()` → `Level2Calculator.calcCourseAchievement()`

$$E_{ik}^{student} = \sum_j \left( C_{ij}^{student} \times w_{jk} \right)$$

**正确性**：✅ 正确。与班级第二级逻辑一致，使用相同的 `Level2Calculator` 和相同的内部权重 $w_{jk}$。

**与规格的关键差异**：
- 规格公式 $E_k = \sum(\bar{C_j} \times w_{jk})$ 使用**班级平均** $\bar{C_j}$
- 学生个人公式 $E_{ik} = \sum(C_{ij} \times w_{jk})$ 使用**个人值** $C_{ij}$

这是正确且必要的设计 — 计算学生个人达成度自然应使用该生自己的目标达成度，而非班级平均。

### 5.5 学生个人第三级（专业级）计算

**代码**：`PersonalAchievementService.persistMajorAchievements()` → `Level3Calculator.calcMajorAchievement()`

$$G_{ik}^{student} = \sum \left( E_{ik}^{student} \times W_{c} \right)$$

**正确性**：✅ 正确。使用的权重 $W_c$ 与专业级第三级计算完全一致（来自 `GlobalCalcService` 归一化后的 `weightRecords`）。

**实现细节**：
1. 首先确保所有相关班级已有 COURSE 级个人数据（无则先计算并持久化）
2. 读取所有学生的 COURSE 级个人数据
3. 逐学生调用 `Level3Calculator.calcMajorAchievement()` 计算 MAJOR 级

### 5.6 学生个人达成度正确性总结

| 维度 | 结论 |
|------|------|
| 计算方式 | ✅ 后端 Java 引擎实时计算，非数据库存储过程 |
| 持久化 | ✅ 计算结果存入 `personal_achievement` 表 |
| 读取优先级 | ✅ DB存储优先，无数据时实时计算回退 |
| 第一级公式 | ✅ 与班级级共用同一引擎，学生个体维度 |
| 第二级公式 | ✅ 使用个人 $C_{ij}$（非班级平均），逻辑正确 |
| 第三级公式 | ✅ 使用与专业级一致的权重，逻辑正确 |
| 事务一致性 | ✅ `@Transactional` 保护，先删后插 |

## 六、发现的问题与建议

### 6.1 中等问题

#### P1：宏观权重自动归一化可能掩盖配置错误

**位置**：`GlobalCalcService.compute()` 第177-195行

**问题**：当多班级分班或原始配置导致指标点权重之和明显偏离 1.0 时，系统静默归一化，不会报错。例如：若某个指标点配置的总权重为 0.5，归一化后所有课程权重翻倍，计算出的 G_k 偏高。

**建议**：在归一化前增加阈值检查，若原始权重之和与 1.0 偏差超过合理范围（如 0.05），应输出警告日志或直接拒绝计算，提示管理员检查宏观矩阵配置。

#### P2：无教学班的课程权重被静默排除

**位置**：`GlobalCalcService.compute()` 第137-141行

**问题**：仅在宏观矩阵中配置但未开设教学班的课程，其权重被静默排除，剩余权重归一化后放大。这可能不是管理员的预期行为。

**建议**：在 dashboard 或计算日志中明确列出"已配置但无教学班"的课程，让管理员知情。

### 6.2 轻微问题

#### P3：权重校验代码重复

**位置**：`Level2Calculator.java` 第29-33行 与 `CourseCalcService.java` 第163-173行

**问题**：内部贡献权重的归一化校验在两处独立实现，逻辑基本一致但错误消息格式不同。

**建议**：统一由 `WeightValidator` 处理，避免维护不一致。

#### P4：Level1Calculator 四参数重载未被使用

**位置**：`Level1Calculator.java` 第26-68行

**问题**：4参数版本的 `calcObjectiveAchievement()` 在所有生产代码路径中均未调用（`CourseCalcService` 和 `PersonalAchievementService` 均使用6参数版本）。

**建议**：若确无用途可移除，或添加 `@Deprecated` 注解标明保留原因。

#### P5：考核点表 `objective_id` 与 N:M 关联表并存

**位置**：`assessment_point.objective_id` + `assessment_objective` 表

**问题**：同一考核点的目标映射存在两个来源。代码优先取 N:M 表，回退取 `objective_id`。但 DB schema 中 `objective_id` 为 NOT NULL，意味着即使有 N:M 绑定也必须填一个值。这造成了数据冗余和潜在不一致（如 N:M 表含目标 A/B，但 `objective_id` 指向目标 C）。

**建议**：长期考虑将 `objective_id` 改为可空或移除，统一使用 N:M 关联表。

### 6.3 数据层面的观察

#### 观察1：部分课程目标达成度异常偏低

从 `obj_achievement` 表数据分析：
- class_id=4（计算机网络-教学班4）：目标 21、22、23、24、25 的达成度分别为 0.0000、0.0000、0.0200、0.0200、0.0000
- class_id=3（计算机网络-教学班3）：目标 19 达成度为 0.0440

这些极低值与同课程其他目标（0.3~0.9）形成巨大反差，可能原因：
1. 该班级确实未参加相关考核
2. 成绩导入不完整
3. 考核点-目标映射配置有误

这不属于计算逻辑问题，但建议在系统中增加异常达成度预警（例如低于 0.3 时标黄提醒）。

#### 观察2：assessment_point.max_score 多为 100.00

除 assessment_point id=14（max_score=40.00）外，所有考核点 max_score 均为 100.00。这意味着系统将每个考核点视为等满分（100分制），实际分数缩放依赖 `weight_percent` 做最终加权。这种设计与 Level1 公式一致（不使用 weight_percent），但需确保教师在录入分数时按考核点自身的满分标准评分。

## 八、专项分析：学生个人第三级"不达标"根因溯源

> **用户反馈**：学生个人第一级、第二级达标（值较高），但第三级大量不达标（值很低），怀疑存在计算错误。

### 8.1 现象确认

以**学生1（陈思远，学号2025010101）**为例，对比各指标点的第二级与第三级：

| 指标点 | 个人第二级（COURSE） | 个人第三级（MAJOR） | 第二级是否"达标" |
|--------|---------------------|---------------------|-----------------|
| 1 | 0.7915（仅class1） | **0.0989** | ✅ 高 |
| 19 | 0.8249（仅class1） | **0.2357** | ✅ 高 |
| 3 | 0.7560~0.8735（4个班） | **0.8129** | ✅ 高 |
| 8 | 0.7636~0.7985（2个班） | **0.6248** | ✅ 高 |

**现象**：同一指标点，第二级（课程维度）可达 0.79~0.87，但第三级（专业维度）骤降至 0.10~0.24（指标点1、19）。

### 8.2 计算验证：逐公式溯源

#### 8.2.1 学生1 / 指标点1 的完整计算链路

**Step 1 — 数据准备**

| 班级 | 课程 | 学生1的 E₁（第二级） | 宏观权重 W |
|------|------|---------------------|-----------|
| class 1 | 数据结构(1) | **0.7915** | 0.1000 |
| class 6 | 大学物理B(4) | 学生1不在该班 | 0.4000 |
| class 5 | 数据库原理(7) | 学生1不在该班 | 0.3000 |
| ~~class ?~~ | ~~学科教学理论与实践(8)~~ | **无教学班！** | ~~0.2000~~ |

**Step 2 — `GlobalCalcService` 权重归一化**

```
原始权重和 = 0.1 + 0.4 + 0.3 = 0.8  (课程8因无教学班被排除)
归一化因子 = 1.0 / 0.8 = 1.25
```

归一化后的有效权重：
- class 1 (数据结构): 0.1 × 1.25 = **0.125**
- class 6 (大学物理B): 0.4 × 1.25 = 0.500
- class 5 (数据库原理): 0.3 × 1.25 = 0.375

**Step 3 — 学生个人第三级计算**

```
G₁(student1) = Σ (E₁ × W_norm)  [仅对学生所在班级求和]
             = 0.7915 × 0.125   [仅 class 1 有该生数据]
             = 0.0989375
             → 四舍五入 0.0989
```

**步骤4 — 与数据库比对**

### 8.3 根因分析

**结论：计算逻辑本身无错误，个人第三级"不达标"由以下两个结构性因素叠加导致。**

#### 根因 1（主要）：部分课程"有矩阵配置但无教学班"→ 权重被排除后归一化放大

当前数据库中存在 **2 门课程无教学班**：

| 课程ID | 课程名 | 涉及的指标点（共11个） |
|--------|--------|---------------------|
| 8 | 学科教学理论与实践 | 1, 4, 6, 19, 25, 26, 28, 29, 30, 31, 32 |
| 11 | 操作系统 | （在 macro_support_matrix 中未找到记录，或未配权重） |

以课程8（学科教学理论与实践）为例，它在宏观矩阵中对 **11 个指标点** 分配了权重（占全专业 32 个指标点的 34%）。由于该课程没有开设教学班：

1. `GlobalCalcService.compute()` 在构建 `validMatrix` 时将其排除
2. 有效权重之和从 1.0 降至 0.6~0.9（取决于指标点）
3. 系统自动触发归一化：剩余课程的权重被等比放大（÷0.6 = ×1.67 至 ÷0.9 = ×1.11）
4. 未修读"被放大"课程的学生，其第三级值反被压低

**示意**（指标点1）：

```
配置态:  [课程1:10%] [课程4:40%] [课程7:30%] [课程8:20%] = 100%
实际态:  [课程1:10%] [课程4:40%] [课程7:30%] [  缺  ]  =  80% → 归一化放大 1.25x
学生1:   [课程1:✓10%→12.5%] [课程4:✗] [课程7:✗]      = 只能拿到 12.5%
```

学生1修了课程1且成绩很好（E₁=0.79），但因为该课程在指标点1中仅占 12.5% 的归一化后权重，即使满分也只能拿 0.125。

#### 根因 2（主要）：`getDashboard()` 未按学期过滤教学班 → 跨学年混合计算

**这是导致"第三级大量不达标"最直接的技术原因。**

**代码证据**：`GlobalCalcService.java`

```java
// 第49行：getDashboard 只接收 majorId，无 semesterId 参数
public DashboardData getDashboard(Long majorId) {
    ...
    for (Course course : courses) {
        // 第68-69行：加载教学班时无任何学期过滤条件
        List<TeachingClass> classes = teachingClassMapper.selectList(
            new LambdaQueryWrapper<TeachingClass>()
                .eq(TeachingClass::getCourseId, course.getId()));
        // ↑ 缺少 .eq(TeachingClass::getSemesterId, semesterId) !
    }
}

// 第109行：compute 收到 semesterId 但从未传给 getDashboard
public MajorCalcResult compute(Long majorId, Long semesterId, Long operator) {
    DashboardData dashboard = getDashboard(majorId);  // ← 丢失了 semesterId
    // semesterId 仅在第208/214行用于存储/删除结果，不参与数据筛选
}
```

**实际影响**：用户触发 `POST /api/global/compute?majorId=1&semesterId=1`（2025-2026学年第一学期），但系统实际加载了 **两个年级、四个学期** 的所有教学班：

| 教学班 | 课程 | 学期ID | 学年 | 年级 |
|--------|------|--------|------|------|
| class 1 | 数据结构 | 1 | 2025-2026秋 | **2025级** |
| class 2 | C语言程序设计 | 1 | 2025-2026秋 | **2025级** |
| class 3 | 计算机网络 | 2 | 2025-2026春 | **2025级** |
| class 4 | 计算机网络 | 1 | 2025-2026秋 | **2025级** |
| class 5 | 数据库原理 | 6 | 2024-2025秋 | **2024级** |
| class 6 | 大学物理B | 6 | 2024-2025秋 | **2024级** |
| class 7 | 线性代数 | 7 | 2024-2025春 | **2024级** |
| class 8 | 高等数学B | 7 | 2024-2025春 | **2024级** |

→ 2024级和2025级全部8个班被打包进同一个计算批次。

**对个人第三级的影响**：

以指标点1为例：
- 权重分配：课程1(10%) + 课程4(40%) + 课程7(30%) + 课程8(20%,无班排除)
- 有效权重归一化：0.8 → ×1.25
- **2025级学生**（仅修课程1）：只能拿到 0.1×1.25=12.5%，第三级 ~0.10
- **2024级学生**（修课程4+7）：能拿到 (0.4+0.3)×1.25=87.5%，第三级可达 ~0.70

→ 同一指标点下，不同年级学生的第三级差异巨大，且与个人能力无关，仅由"是否修了高权重课程"决定。

#### 根因 3（次要）：学生分属不同年级，课程互不重叠

即使修复了学期过滤，以下结构性因素仍然存在：

| 群体 | 入学年份 | 所在班级 | 修读课程 |
|------|---------|---------|---------|
| 2025级 | 2025 | class 1,2,3,4 | 数据结构、C语言、计算机网络 |
| 2024级 | 2024 | class 5,6,7,8 | 数据库原理、大学物理B、线性代数、高等数学B |

**两个群体修读的课程完全不重叠**。即使按学期分别计算，宏观矩阵中每个指标点仍由多个课程共同支撑，而学生在单个学期内只修读了其中一部分。

#### 根因本质：两个 Bug 叠加产生"第三级不达标"

**Bug A（代码缺陷）**：`getDashboard()` 未按学期过滤教学班。即使用户指定了 `semesterId`，系统仍将所有学期（2024-2025、2025-2026）的班级混在一起计算。

**Bug B（配置问题）**：课程8无教学班导致权重排除+归一化畸变，放大了 Bug A 的影响。

**叠加效应**：

```
专业第三级 G_k = Σ_{所有8个班} E_k × W_c = 0.7224 ✅ 正确（全专业维度）

个人第三级 G_ik = Σ_{该生所在班} E_ik × W_c（W_c 用全部8个班归一化）
    2025级学生: Σ_{class1-4} → 只覆盖约 30-80% 的有效权重 → 值低
    2024级学生: Σ_{class5-8} → 只覆盖约 30-80% 的有效权重 → 值低
```

正确的行为应该是：触发 `compute(majorId=1, semesterId=1)` 时，只加载 2025-2026 学年的 class 1-4，用这4个班的权重归一化计算。2024级的 class 5-8 应在 `semesterId=6` 或 `semesterId=7` 时单独计算。

### 8.5 修复建议（按优先级排列）

#### 🔴 建议1（代码缺陷 — 必须修复）：`getDashboard()` 增加学期过滤

**位置**：`GlobalCalcService.java` 第49-103行

**当前代码**（第68-69行）：
```java
List<TeachingClass> classes = teachingClassMapper.selectList(
    new LambdaQueryWrapper<TeachingClass>()
        .eq(TeachingClass::getCourseId, course.getId()));
// ↑ 缺少 .eq(TeachingClass::getSemesterId, semesterId) !
```

**修复方案**：为 `getDashboard()` 增加 `semesterId` 参数，过滤教学班：
```java
public DashboardData getDashboard(Long majorId, Long semesterId) {
    ...
    List<TeachingClass> classes = teachingClassMapper.selectList(
        new LambdaQueryWrapper<TeachingClass>()
            .eq(TeachingClass::getCourseId, course.getId())
            .eq(semesterId != null, TeachingClass::getSemesterId, semesterId));
    ...
}
```

相应地，`compute()` 第111行改为：
```java
DashboardData dashboard = getDashboard(majorId, semesterId);
```

**效果**：确保 `POST /api/global/compute?majorId=1&semesterId=1` 只加载 2025-2026 学年的 class 1-4，2024-2025 学年的 class 5-8 在 `semesterId=6` 或 `7` 时单独计算。两个年级不再混合。

> **这是"第三级个人不达标"最直接的修复方案，此修复后 2025 级学生的个人第三级将仅基于 class 1-4 的权重归一化，与 2024 级完全解耦。**

#### 🟡 建议2（数据层）：补充缺失的教学班或移除无班课程的权重

课程8（学科教学理论与实践，覆盖11个指标点）和课程11（操作系统）在宏观矩阵中有配置但无教学班。

- **方案A**：在 `teaching_class` 表中为这两门课程创建教学班，分配学生并导入成绩。
- **方案B**：若课程8、11在当期确实不开设，从 `macro_support_matrix` 中移除其权重记录。

#### 🟡 建议3（架构层 — 中期）：个人第三级按学生已修课程做组内归一化

即使修复了学期过滤，单个学期/年级内学生仍可能未修读某指标点的全部支撑课程。建议个人第三级改为对学生已修课程进行**组内归一化**：

$$G_{ik}^{student} = \frac{\sum_{c \in S_i} (E_{ikc} \times W_c)}{\sum_{c \in S_i} W_c}$$

其中 $S_i$ 为学生 $i$ 已修读的支撑课程集合。

#### 🟢 建议4（产品层）：在 UI 中增加上下文说明

在学生个人达成度页面标注"当前统计基于已修读的 N 门课程（该指标点共 M 门支撑课程）"。
